Accesos y conexiones del cliente — propuesta de ampliación

Explorando qué le falta a la pestaña "Accesos y conexiones" para reemplazar de verdad a los Cuadernos de Teamwork, antes de convertirlo en una observación formal.

Origen: OBS-0001 · Spec 018-cliente-accesos-conexiones Estado: Sin socializar Fecha: 27 de julio de 2026

En resumen

  • El modelo actual (vpn, system_url, remote_desktop) no tiene forma de representar un acceso a base de datos ni a un servidor/instancia/VM sin forzar el tipo.
  • No existe un campo puerto propio — hoy se concatena a mano dentro del host.
  • environment (Producción/Pruebas) solo aplica cuando el tipo es system_url, pero en la práctica también aplica a VPN y bases de datos.
  • El manual de conexión solo puede adjuntarse a nivel de cliente en general — no se puede anclar a un acceso puntual cuando hay varios.
  • Corrección tras revisar un caso real: un acceso (ej. un ERP Cloud, un OIC) suele tener una sola URL compartida por varios usuarios, cada uno con su propia credencial. Modelarlo como "1 acceso = 1 usuario" obliga a repetir la URL por cada persona.
  • El "tipo de acceso" (VPN, Base de datos…) no debe ser un enum fijo en código — debe ser un catálogo administrable (mismo patrón que "Equipo"), para poder agregar APEX, NetSuite, etc. sin depender de un despliegue.

Nota para quien lo implemente (persona o IA)

Este documento es una sugerencia exploratoria para discutir, no una especificación aprobada ni una instrucción para ejecutar tal cual. Úsalo como contexto de la idea y del problema real que la origina; el alcance final, los nombres de campos y el diseño de UI se deben validar contra el spec vivo (specs/018-cliente-accesos-conexiones/) y registrar como observación en UAT/02_Backlog/BACKLOG.md antes de construirse.

Contexto

Hoy uso los Cuadernos de Teamwork para guardar los accesos técnicos de cada cliente: instancias, máquinas virtuales, VPNs, bases de datos, credenciales y, muchas veces, el manual o instructivo de cómo conectarse. Por costo y por funcionalidades que necesito, estoy migrando la gestión de proyectos a mi propia aplicación.

La pestaña "Accesos y conexiones" de TICKET_SYW ya resolvió el problema original (OBS-0001): antes solo existían dos columnas sueltas en el cliente, vpn_ips y vpn_credentials. Ahora es una tabla de registros múltiples. Pero al usarla para reemplazar de verdad los Cuadernos, aparecen límites que el spec original no cubría.

Cambios de modelo propuestos

CampoHoyPropuestaPor qué
client_access
(usuario, password)		 Usuario y contraseña viven en la misma fila que el host — 1 acceso = 1 credencial Se separan en una tabla hija nueva: client_access_credentials Un mismo host (ERP, OIC, APEX) puede tener N usuarios; hoy obliga a repetir la URL por cada uno
client_access_credentials
(nueva tabla)		 No existe id, client_access_id (FK), etiqueta, username, password (cifrado), notes 1 acceso ──< N credenciales. Una contraseña compartida entre varios usuarios simplemente se repite como valor — no requiere modelado especial
access_type Enum fijo de aplicación: vpn · system_url · remote_desktop (solo se amplía con un despliegue de código) FK a catálogo administrable catalog_access_types — el usuario agrega tipos nuevos (APEX, NetSuite…) desde el módulo Catálogos, sin tocar código Mismo patrón ya usado en catalog_teams (OBS-0024): un catálogo, no un enum, cuando el usuario necesita ampliarlo él mismo
environment Solo si access_type = system_url Aplica a cualquier tipo VPN y base de datos también distinguen Producción/Pruebas en la práctica

client_access_attachments

Los tipos de acceso, como catálogo — no como enum fijo

Igual que ya pasó con "Equipo" (OBS-0024, catálogo catalog_teams administrable desde Catálogos), "Tipo de acceso" deja de ser una lista fija en el código. Se administra desde la misma pantalla de Catálogos: agregas "APEX", "NetSuite", lo que necesites, y aparece disponible de inmediato al crear un acceso.

El color no lo elige el usuario a mano — evita combinaciones ilegibles o dos tipos casi del mismo color. Cada tipo nuevo toma automáticamente el siguiente color disponible de una paleta fija de 8, pensada para verse bien en modo claro y oscuro; una vez asignado, ese color no cambia aunque se agreguen más tipos después.

  • VPN4 accesos
  • Base de datos2 accesos
  • Servidor / instancia1 acceso
  • Escritorio remoto1 acceso
  • Sistema / Integración2 accesos
  • APEX — agregado hoy1 acceso
  • NetSuite — agregado hoy0 accesos

Al agregarlos, "APEX" y "NetSuite" quedan disponibles para clasificar accesos de inmediato — con su propio color, agrupando igual que los demás:

Cómo se vería en el modal del cliente

Misma composición ya aprobada en la Decisión 6 del spec 018 (pestañas dentro del modal existente): se conserva la pestaña. Lo que cambia es que la tabla plana de accesos pasa a ser una lista de instancias, cada una expandible a sus credenciales — igual al patrón "Portafolio de software" pero con un nivel más de anidación.

Qué no cambia (seguridad)

  • La contraseña se sigue cifrando con el mismo mecanismo ya vigente para vpn_credentials, ahora en client_access_credentials.password. Un Client Secret de OAuth se guarda en esa misma columna — es un secreto igual que una contraseña, no necesita un cifrado distinto.
  • RLS ya está habilitado en client_access y client_access_attachments con el mismo patrón de client_contacts; la tabla nueva client_access_credentials y las columnas nuevas quedan cubiertas por la misma policy, sin crear una variante.
  • El enmascarado por defecto se mantiene: toda contraseña sigue oculta tras •••••••• hasta que alguien la revela explícitamente con el botón, igual que hoy.
